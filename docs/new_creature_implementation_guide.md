# SUMMONS CODE 新規クリーチャー実装ガイド

更新日: 2026-09-05  
対象バージョン: v1.57以降

## 1. 目的

ユーザーから新規クリーチャーの実装依頼を受けた際に、企画の確認、カード設定、能力処理、画像、テレビ・スマホUI、公開カード一覧、保存互換、テスト、リリースまでを漏れなく進めるための手順書。

`server.js`をゲームルールとカード定義の正とし、クライアントだけに能力やカード情報を追加しない。実装時は本書の全項目を機械的に適用するのではなく、能力の種類に応じて「6. 影響範囲」を確認し、必要な箇所だけを変更する。

## 2. 実装前に確定する項目

### 2.1 カード基本情報

- [ ] 進化前の名前
- [ ] 進化後の名前、または進化なし
- [ ] 英数字のカードID
  - 小文字のsnake_caseを使用する
  - 進化前を`<id>`、進化後を自動生成される`<id>_f`として扱う
  - 既存ID、スペルID、ウェポンIDと重複させない
- [ ] 属性: `fire` / `water` / `earth` / `wind` / 無属性
- [ ] レアリティ: `N` / `R` / `L`
- [ ] 召喚コスト
- [ ] 進化前のAT・HP
- [ ] 進化後のAT・HP
- [ ] 進化前の能力名と効果文
- [ ] 進化後の能力名と効果文
- [ ] 共通山札・ショップに入れる枚数
  - 原則はN=3枚、R=2枚、L=1枚
  - 例外枚数は明示して確定する
- [ ] 初期デッキへ入れるか。指定がなければ市場・ドラフトのみとする
- [ ] 支給アートのファイルと、進化前後の対応

### 2.2 能力ルール

効果文だけでなく、以下の判定条件を確定する。未確定部分がゲーム結果を変える場合は実装前にユーザーへ確認する。

- [ ] 発動タイミング
  - 召喚時、配置時、進化時、ターン開始時、移動中、着地時、戦闘前、攻撃時、防衛時、勝利時、敗北時、回復時、廃棄時など
- [ ] 発動対象
  - 自分、味方、敵、土地、手札、山札、廃棄、全体、任意選択など
- [ ] 対象が0件の場合の挙動
- [ ] 効果量、上限、下限、丸め方
- [ ] 複数体配置時に重複するか
- [ ] 進化前後で能力が同じか、強化・置換されるか
- [ ] 所有権、土地属性、クリーチャー属性のどれを参照するか
- [ ] 一時的な属性変更や負傷など、現在値と初期値のどちらを参照するか
- [ ] 他効果との計算順序
- [ ] 無効化、耐性、結界、先制、直接移動などの例外
- [ ] 召喚元や対象が移動・交代・撃破・回収・売却・破産した時の解除条件
- [ ] セーブ・復元後も保持する状態
- [ ] プレイヤーに見せるログ、メッセージ、カード演出
- [ ] BOTが対象を選ぶ基準

## 3. 実装の基本手順

### Step 1: 現状確認と変更範囲の決定

- [ ] `git status -sb`で既存変更と未追跡ファイルを確認する
- [ ] `server.js`の類似能力と既存テストを検索する
- [ ] 同じ処理を行う共通関数がある場合は必ず再利用する
  - 回復量は実際に回復したHPを集約する処理
  - 通行料は通行料計算処理
  - 移動は1歩ずつ解決する移動処理
  - 配置時効果は配置後の共通フック
  - 戦闘補正は戦闘解決処理
- [ ] 既存のゲームルールを変えるのか、新カードだけの例外なのかを区別する
- [ ] バージョン番号と専用テストファイル名を決める

### Step 2: `server.js`へカードを定義

`CREATURES`へ進化前カードだけを追加する。

```js
sample_id: {
  name: '進化前名',
  evo: '進化後名',
  elem: 'water',
  st: 20,
  hp: 40,
  cost: 100,
  evoSt: 40,
  evoHp: 60,
  fx: '【能力名】効果文',
  evoFx: '【進化後能力名】効果文',
  rarity: 'R',
},
```

- [ ] 進化後の`<id>_f`を直接定義しない
- [ ] 進化後は既存の自動生成処理で作られることを確認する
- [ ] 進化なしの場合は`evo`、`evoSt`、`evoHp`、`evoFx`を持たせない
- [ ] 効果名は`【】`で囲み、ゲーム内表示と公開カード一覧で同じ文章を使う
- [ ] `MARKET_POOL`へ進化前IDだけを追加する
- [ ] レアリティ標準と異なる枚数は`MARKET_COPY_OVERRIDES`へ追加する
- [ ] `makeDeck()`と`shopRandomPool()`の両方が同じ枚数設定を参照することを確認する
- [ ] 進化後IDが共通山札・ショップ抽選へ直接混入しないことを確認する
- [ ] 初期デッキ採用が確定している場合だけ`STARTER_DECKS`を変更する

### Step 3: 能力処理を実装

- [ ] 効果の発生源を1か所に集約する
- [ ] 同じイベントを複数の呼び出し元から二重発火させない
- [ ] 進化判定は既存の`baseId()`、`isEvolved()`の考え方に合わせる
- [ ] 通常召喚、交代配置、侵略成功配置のうち、どれで発動するかを明示する
- [ ] 効果値をゲームログと公開状態用に再計算せず、同じ計算関数を利用する
- [ ] 効果処理後の再開先が、手番終了・ダイス待ち・戦闘後処理のどれかを確認する
- [ ] 選択必須の効果は通信失敗後もpendingを残し、再操作可能にする
- [ ] 候補消失時、対象0件時、プレイヤー破産時に操作不能にならないようにする

選択操作がある場合:

- [ ] 既存`ask()`形式のpendingを利用する
- [ ] pending名と選択肢ID接頭辞を重複しない名前で決める
- [ ] サーバーで選択肢を再検証し、クライアントから任意の対象を送れないようにする
- [ ] スマホのpending見出し、対象発光、決定・キャンセル・再開導線を実装する
- [ ] BOT用の選択ロジックを追加する
- [ ] `ui_test.js`の全pending貫通で停止しないことを確認する

永続状態を追加する場合:

- [ ] 状態をクリーチャー、土地、プレイヤー、ルームのどこへ保持するか決める
- [ ] 移動・交換時に一緒に移す状態と、その場へ残す状態を区別する
- [ ] 撃破・回収・売却・所有権変更・破産時の掃除処理を実装する
- [ ] 復元時と状態配信前に不正・古い状態を除去するreconcile処理を用意する
- [ ] 新フィールドを任意項目として扱い、旧セーブを読み込めるようにする

### Step 4: 公開状態と演出データを追加

- [ ] テレビ・スマホに必要な最小情報だけを`publicState()`へ追加する
- [ ] 手札や未公開カードなど、他プレイヤーに見せてはいけない情報を含めない
- [ ] 演出の重複防止に一意な時刻・世代・イベントIDの既存方式を使う
- [ ] アニメーション時間と操作解放時刻を一致させる
- [ ] 移動歩数を変える能力は、出目ではなく実移動歩数を公開する
- [ ] 資産や戦況を動かす能力は、試合振り返り用の資産記録・転換点への影響を確認する

### Step 5: 画像アセットを生成

支給元画像は上書きせず、バージョン別の変換スクリプトを`/scripts`へ置く。直近の`prepare_v*_assets.py`をテンプレートとして使用する。

進化ありの場合の標準出力:

| 用途 | 進化前 | 進化後 | 標準仕様 |
|---|---|---|---|
| 盤面・戦闘・スマホ | `public/assets/c_<id>.png` | `public/assets/e_<id>.png` | 300×300、RGBA、透過、黒アウトライン |
| カード一覧・ショップ | `public/assets/cards/c_<id>.webp` | `public/assets/cards/e_<id>.webp` | 1024×1024、透過、余白を保持 |

- [ ] IDとファイル名を完全一致させる
- [ ] 透明背景を保持する
- [ ] 顔・武器・尻尾などが切れていないことを確認する
- [ ] 盤面用画像は縮小時にも輪郭が読める黒アウトラインを付ける
- [ ] 不要な透明余白を整理しつつ、カードごとの見た目の大きさを揃える
- [ ] `catalog.artIds`へ起動時の自動走査でIDが入ることを確認する
- [ ] 専用アイコンや状態バッジが必要なら、用途名とバージョンを含む別アセットにする
- [ ] 生成物の形式、寸法、アルファチャンネル、ファイル容量をテストする

### Step 6: 各画面へ反映

カード定義と画像命名が正しければ多くは公開カタログから自動反映される。ただし、全画面を目視確認する。

スマホ:

- [ ] 手札
- [ ] 通常ドロー・ランダムドロー
- [ ] 2～3枚の選択ドロー
- [ ] ドラフト・廃棄・鍛錬などの選択画面
- [ ] デッキ一覧
- [ ] カード一覧・進化前後切り替え
- [ ] タップ・長押し詳細
- [ ] ショップ一覧・ショップ詳細
- [ ] 戦闘ウェポン代用など、クリーチャーが別用途で表示される画面
- [ ] 専用pendingの対象選択UI
- [ ] 土地詳細・ミニマップの能力状態

テレビ:

- [ ] 盤面の進化前・進化後アート
- [ ] 召喚、進化、侵略、撃破、帰還の演出
- [ ] 戦闘画面の名前、AT、HP、能力補正、注釈
- [ ] ショップ表示
- [ ] 専用メッセージ、カットイン、ログ
- [ ] DOM版とPhaser版の表示差
- [ ] 状態アイコン、通行料、プレイヤーコマとの重なり
- [ ] `prefers-reduced-motion`時の代替表示

公式ホームページ:

- [ ] `/api/catalog`に進化前後の情報と画像URLが出る
- [ ] `/cards`で名前・進化後名・効果文の検索ができる
- [ ] 属性・レアリティ・カテゴリ絞り込みに出る
- [ ] モーダルで進化前後を切り替えられる
- [ ] `/rules`へ新能力の例外・計算順を追記する
- [ ] カード件数・進化数のフォールバック値を更新する

### Step 7: ドキュメントとバージョンを更新

- [ ] `server.js`の`VERSION`
- [ ] `package.json`の`version`
- [ ] 既存のバージョン固定テスト
- [ ] `public/site/cards.html`のフォールバックバージョン・件数
- [ ] `public/site/rules.html`のバージョン・更新日
- [ ] `docs/spec_rules.md`へ正確な内部仕様
- [ ] `docs/manual.md`へプレイヤー向けの短い説明
- [ ] 共通山札総数、クリーチャー数、進化組数などの記載
- [ ] 専用テストを`package.json`の`pretest`と`test:vXXX`へ追加

## 4. 専用テストに含める項目

新しいリリースごとに`vXXX_<feature>_test.js`を作り、カード固有の挙動を直接検査する。

### 4.1 カード定義

- [ ] ID、名前、進化名、属性、レアリティ、コスト
- [ ] 進化前後のAT・HP
- [ ] 進化前後の効果文
- [ ] `<id>_f`が正しく自動生成される
- [ ] 進化なしカードに不要な進化形がない

### 4.2 山札・ショップ・カタログ

- [ ] 共通山札の採用枚数
- [ ] ショップ抽選の重み
- [ ] 進化後カードが直接混入しない
- [ ] 共通山札総数の更新
- [ ] 公開カード総数、クリーチャー数、進化数の更新
- [ ] `/api/catalog`に公開可能な情報だけが含まれる
- [ ] カード用画像URLが正しい

### 4.3 能力の正常系

- [ ] 進化前の効果量
- [ ] 進化後の効果量
- [ ] 攻撃側・防衛側の両方で必要な効果
- [ ] 通常召喚、交代配置、侵略成功配置など全対象経路
- [ ] 土地レベル、属性、所有数、負傷量など境界値
- [ ] 複数体配置時の重複ルール
- [ ] 他効果と同時に発生した場合の計算順
- [ ] ログ・公開イベントの内容

### 4.4 能力の異常系・非発動系

- [ ] 対象が0件
- [ ] 自分と敵を取り違えない
- [ ] 最終地点、直接移動、無効化中などの除外条件
- [ ] 0回復、0ダメージ、0Gなど実変化がない場合
- [ ] 上限・下限を超える入力
- [ ] 同じイベントの再送・再評価で二重発火しない
- [ ] 不正な選択肢IDを拒否する
- [ ] 効果元・対象消失後に古い効果が残らない

### 4.5 BOT・保存・公開状態

- [ ] BOTが必須pendingを自動解決できる
- [ ] BOTの選択基準が期待どおり
- [ ] 効果発動前、pending中、発動後を保存・復元できる
- [ ] 旧バージョンのセーブを読み込める
- [ ] 復元時に不正な古い状態を掃除できる
- [ ] 公開状態に必要な情報が出る
- [ ] 非公開カード情報を漏らさない

### 4.6 画像・UI

- [ ] 盤面PNGが300×300、RGBA、透過あり
- [ ] カードWebPが正しい形式と寸法
- [ ] 進化前後で画像を取り違えない
- [ ] 手札・ドロー・選択・デッキ・図鑑・ショップで名前と本文が見切れない
- [ ] 専用pending、カード演出、状態バッジのDOMが存在する
- [ ] Phaser側にも同じ表示がある
- [ ] イベントの重複再生を防止している

## 5. 実行する検証

### 5.1 自動検証

```powershell
node --check server.js
npm.cmd run test:vXXX
npm.cmd test
git -c safe.directory='<checkout>' diff --check
```

`npm.cmd test`では最低限、次がすべて成功することを確認する。

- Phaser回帰
- タイミング・同期
- 過去バージョン固有テスト
- BOT戦複数回完走
- BOTモード
- 全pending UI貫通
- セーブ・復元
- ホームページ・カード一覧回帰

### 5.2 目視検証

テレビ:

- [ ] 1280×720
- [ ] 1366×768
- [ ] 1920×1080

スマホ横画面:

- [ ] 667×375
- [ ] 844×390
- [ ] 896×414

確認内容:

- [ ] カード名、効果文、AT・HP、コストが切れない
- [ ] 進化前後の画像と効果が一致する
- [ ] ボタン、吹き出し、状態バッジ、コマが重ならない
- [ ] タップ、長押し、ドラッグ、決定、キャンセルが従来どおり動く
- [ ] 実際の発動条件でテレビ演出とスマホ操作解放が同期する
- [ ] 長い試合や複数配置でも表示・処理が重複しない

到達に時間がかかる能力には、既存の`fixture`方式へ表示例を追加する。ただしfixture専用データを通常ゲームへ混入させない。

## 6. 能力種別ごとの影響範囲

| 能力種別 | 主なサーバー処理 | 特に確認する画面・データ |
|---|---|---|
| ステータスのみ | `CREATURES`、進化生成、山札・市場 | 全カード表示、戦闘、カタログ件数 |
| 召喚・配置時 | 配置後共通フック、配置理由、pending再開 | 空き地召喚、交代、侵略成功、BOT |
| 戦闘補正 | 戦闘開始・攻防値計算・戦闘ログ | 攻撃側、防衛側、先制、ウェポン、地形補正 |
| 勝敗後 | 戦闘後処理、報酬、撃破・帰還 | 勝者・敗者両側、侵略成立、連続効果 |
| 回復連動 | 実回復量の共通集計 | 0回復、複数対象、複数効果元、報酬演出 |
| 移動中・強制停止 | 1歩単位の移動、`lastDice`、着地処理 | 城・門通過、周回、実移動歩数、操作解放時刻 |
| 通行料・資産 | 通行料計算、支払い、資産記録 | 割合と固定値の順序、破産、試合振り返り |
| 土地属性・連鎖 | 実効属性、属性上書き、連鎖計算 | 元属性との違い、属性変更後、称号・資産 |
| 手札・山札・廃棄 | ドロー、追加、廃棄、追放、枚数上限 | 非公開情報、二重発火、山札切れ、手札上限 |
| 永続マーカー | 状態保存、reconcile、公開状態 | 移動・交換・喪失・破産、セーブ復元、バッジ |
| 対象選択 | pending、選択肢検証、BOT評価 | ミニマップ発光、決定・キャンセル、候補消失 |
| 専用カットイン | 公開イベント、表示キュー、重複ID | テレビ、モーション軽減、SSE再送、表示時間 |

## 7. 変更ファイルの目安

必須になりやすいファイル:

- `server.js`: カード定義、山札、市場、能力、公開状態、バージョン
- `public/assets/c_<id>.png`: 進化前の盤面用画像
- `public/assets/e_<id>.png`: 進化後の盤面用画像
- `public/assets/cards/c_<id>.webp`: 進化前のカード用画像
- `public/assets/cards/e_<id>.webp`: 進化後のカード用画像
- `scripts/prepare_vXXX_assets.py`: 再生成可能な画像変換
- `vXXX_<feature>_test.js`: 専用回帰テスト
- `package.json`: バージョンとテスト登録
- `docs/spec_rules.md`: 詳細仕様
- `docs/manual.md`: プレイヤー向け説明
- `public/site/cards.html`: フォールバック件数・バージョン
- `public/site/rules.html`: 公開ルール・更新日

能力に応じて変更するファイル:

- `public/phone.html`: pending、ミニマップ、詳細、専用演出
- `public/board.html`: テレビDOM表示、戦闘、カットイン、状態バッジ
- `public/board_world.js`: Phaser盤面、移動・召喚・撃破演出
- `save_test.js`: 新しい永続状態
- `ui_test.js`: 新pending
- `bot_test.js` / `bot_mode_test.js`: BOT判断や完走条件
- `timing_test.js`: 新演出と操作解放時刻
- `v154_site_pages_test.js`: カード一覧・ルールの件数や表示
- `v157_phone_card_text_test.js`: 長い効果文のスマホ表示

## 8. よくある実装漏れ

- カードIDと`c_<id>.png`の名前が違い、アートが表示されない
- 進化後画像を`e_<id>.png`ではなく`c_<id>_f.png`で置いてしまう
- `CREATURES`へ追加したが`MARKET_POOL`へ入れていない
- 山札枚数だけ変更し、ショップ抽選の重みが違う
- 進化後カードを共通山札へ直接入れてしまう
- 通常召喚だけ対応し、交代配置や侵略成功配置で発動しない
- テレビに表示を足したが、サーバーの公開状態に根拠データがない
- スマホのpendingを足したが、BOTが選べずゲームが停止する
- 効果元の消滅後も土地マーカーや補正が残る
- 元の土地属性を数え、現在の実効属性を数えていない
- 回復予定量を数え、実際に回復したHPを数えていない
- SSE再送や複数フックで収入・ダメージ・演出が二重発火する
- 能力のログと実計算が別実装になり、表示値がずれる
- カード本文が手札では読めても、ドロー・デッキ一覧・ショップで見切れる
- カード総数、進化数、共通山札総数、公開ルールの更新を忘れる
- 新フィールドを必須扱いにし、旧セーブが読み込めなくなる
- 専用テストだけ通し、BOT完走・全pending・保存復元を実行しない

## 9. 完了条件

以下をすべて満たして初めて「実装完了」とする。

- [ ] ユーザーと確定した数値・効果・例外条件どおりに動く
- [ ] 進化前後、全発動経路、非発動条件を専用テストで検査している
- [ ] 山札・ショップ・公開カタログ・カード一覧の件数が一致する
- [ ] テレビとスマホの全該当表示で画像と文章を確認している
- [ ] BOTが必須選択を処理し、試合を完走できる
- [ ] セーブ・復元と旧セーブ互換を確認している
- [ ] 非公開情報が公開状態へ漏れていない
- [ ] `npm.cmd test`が全件成功する
- [ ] `git diff --check`が成功する
- [ ] 関係する仕様書とプレイヤー向け説明を更新している

## 10. コミット・本番反映を依頼された場合

- [ ] 関係ファイルだけを個別にステージする。`git add .`は使用しない
- [ ] 未追跡の画像、`output/`、`tmp/`、作業用生成物を含めない
- [ ] コミットSHAを記録する
- [ ] GitHub `main`のSHAがローカルHEADと一致することを確認する
- [ ] Lightsailの自動デプロイ完了を待つ
- [ ] `https://summonscode.jp/api/fixture`のバージョンを確認する
- [ ] `/`、`/phone`、`/cards`、`/rules`と新規アセットURLを本番確認する
- [ ] 本番確認が終わるまで「本番反映完了」と報告しない

本番はメモリ上に対戦ルームを保持しているため、サーバー再起動で進行中ルームへ影響する。公開タイミングを選べる場合は、プレイ中の利用者が少ない時間を選び、詳細は`docs/deploy_lightsail.md`に従う。
