# セーブ/再開機能 実装計画(v0.62候補)

状態: **実装済み(v0.62)**。実装された挙動の記録は`spec_save_v0.62.md`を参照。本書は設計経緯とレビュー対応の記録として保持。§7の最終方針が§1-2の記述に優先する。

## 0. 背景・目的

- 1ゲームが長く(昼休みに収まらない)、**途中中断→後日再開**が必要になった。
- サーバー(Render)は全状態をメモリにしか持たず、再起動・デプロイ・60分無操作クローズでルームが消える。
- サーバーにDB/永続ディスクを足さず、**盤面を開いているブラウザを保存場所にする**方式を採る。

## 1. 全体像

```
[ゲーム中]  盤面ブラウザが手番が変わるたびに /api/save を呼ぶ
             → ルーム全状態のJSONをlocalStorageへ自動保存
[中断]      何もしなくてよい(ブラウザを閉じてOK)
[再開]      タイトルに「続きから再開」→ /api/restore で同じコード・同じIDのルームを復元
             → スマホは各自ページを開くだけで自動復帰(復帰できない端末はコード+名前で救済)
```

- 保存の実体は「盤面を開いているPCのブラウザ内(localStorage)」。ファイルではない。
- 保険として「ファイルに書き出し/ファイルから再開」(JSONダウンロード/読み込み)を付け、別PCでも再開可能にする。

## 2. 実装ステップ

### Step 1: サーバー ─ 直列化と復元(コア)

- `serializeRoom(r)`: ルームの完全な状態をJSON化
  - **含める**: code / phase / turn / round / players一式(山札・手札・捨て札・廃棄・選択ドロー中の候補pickCards・所持金・位置・刻印・宝石・ULT使用済み・spellCast等) / owners / elemOv / tileFx / curses / barrier / titles / treasureCost / 共通山札deck / draft / battle / pending / log(直近50件程度)
  - **除外**: SSE接続(clients)・タイマーID(pickTimer等)
  - `saveVer`(セーブ形式バージョン)と`gameVer`(実装バージョン)を刻印
- `restoreRoom(data)`: 検証(形式・必須フィールド)→ ルーム再構築
  - **同じルームコード・同じプレイヤーIDで復元**(スマホの自動復帰(sc_session)をそのまま効かせる)
  - コード衝突時: 既存ルームが無人なら差し替え、有人ならエラー
  - pendingが`pick_draw`なら10秒タイマーを張り直す(制限時間はリセット)
  - gameVer不一致は「読めるが警告」
- API: `GET /api/save?room=CODE` / `POST /api/restore`

### Step 2: 盤面(board.html)─ 自動セーブとUI

- SSEで`state.turn`または`round`が変わるたびに`/api/save`→`localStorage['sc_save']`へ上書き(スロット1つ)
- タイトル画面: セーブがあれば「続きから再開(第N周・キャラ名…)」+保存日時を表示
- 「ファイルに書き出す」/「ファイルから再開」ボタンをタイトルに配置
- 再開後は通常ルームとして動作(自動セーブ継続)
- UI設計思想に従う: 絵文字なし・タイトル画面の全画面レイアウト内に配置

### Step 3: スマホ(phone.html)─ 名前による復帰救済

- ゲーム進行中のルームへコード+名前で参加しようとした場合、同名プレイヤーがいれば**そのプレイヤーとして引き継ぐ**(`/api/join`拡張)
- 対象ケース: 別ブラウザで開いた/サイトデータを消した端末(通常の自動復帰はlocalStorage任せで現状のまま)

### Step 4: テスト

1. **単体テスト(往復)**: セーブ→復元→全フィールド一致。境界状態: 選択ドロー中/ドラフト中/戦闘の支援選択中/破産処理中/手札超過中
2. **bot回帰の拡張**: BOT対戦を途中(例: 200手)でserialize→restoreして続行し、完走+カード保存則を確認(最重要の検証)
3. **実ブラウザ**: ①数ターン→盤面を閉じる→開き直して再開→スマホ自動復帰 ②スマホのデータ消去→名前復帰 ③ファイル書き出し→localStorage消去→ファイル読み込み再開
4. 既存の`npm test`一式

### Step 5: ドキュメント

- `docs/spec_save_v0.62.md`(実装時に本計画を仕様化)、manual/spec_rulesへ追記、CLAUDE.md更新

## 3. リスク・注意点

| 項目 | 内容 |
|---|---|
| 秘匿情報 | セーブJSONには全員の手札・山札が平文で入る(盤面PCを覗けば見える)。身内プレイ前提で許容 |
| セーブの鮮度 | 自動セーブは手番の変わり目 → 最悪1手番ぶん巻き戻る(演出途中を保存しないためむしろ安全) |
| バージョン更新 | カード追加・ルール変更後に古いセーブを読むと不整合の可能性 → gameVer警告+読めなければ諦める割り切り |
| Render再起動 | 復元はクライアント主導なので問題なし(この対策そのもの) |

## 4. 規模感

- 変更は server.js + 両HTML。テスト込みで1セッション規模。
- 既存ロジックへの影響はほぼゼロ(直列化=読み取り専用、復元=ルーム新規作成の亜種)。

## 5. 実装前にオーナーが決めること(回答済み 2026-07-21)

1. セーブスロットは1つ(新しいゲームを始めると上書き)でよいか → **OK**
2. コード衝突時、有人ルームならエラー(強制上書きしない)でよいか → **OK**(§7でさらに「原則拒否」に強化)
3. 名前復帰は「同名がいたら即引き継ぎ」か「盤面側で承認」か → **即引き継ぎ**(§7のP1-3に緩和策あり)

## 6. レビュー指摘事項(実装前に反映)

### 必須対応(P1)

1. **保存スキーマを完全に定義する**
   - 現在の列挙には`market`が含まれていない。加えて`duel` / `winner` / `lastBattle` / `lastDice` / `lastDraw` / `lastEvent` / `lastGain` / `lastRuin` / `lastSeal` / `lastUlt` / `halfMarket` / `dirPend` / `atSeq`等を、永続状態・表示用履歴・ランタイム状態に分類する。
   - `clients` / タイマーID / `lastActivity`等のランタイム状態だけを明示的に除外し、保存対象の追加漏れを検出するテストを置く。
   - 往復テストは既知フィールドの一致だけでなく、ルームに新しい永続フィールドが追加された際に未分類のまま通らない仕組みにする。

2. **保存・復元APIを盤面だけに認可する**
   - ルームコードは参加者全員が知るため認証情報として扱わない。
   - ルーム作成時に十分長いランダムな`boardToken`を発行し、`/api/save`、`/api/restore`、`/api/close`はそのトークンを必須にする。
   - 復元JSONにはリクエストサイズ上限を設け、オブジェクト形状、配列長、数値範囲、カードID、プレイヤーIDの一意性、参照整合性を検証する。

3. **名前だけの即時引き継ぎを採用しない**
   - 名前を知るだけで他プレイヤーの手札閲覧・代理操作ができるため、盤面側の承認、またはゲーム開始時に発行する復帰用PINを必須にする。
   - 推奨案は「コード+名前+復帰用PIN」。名前比較時の空白・大文字小文字・重複名の扱いも仕様化する。

4. **自動セーブの契機を`turn` / `round`だけにしない**
   - ロビーからゲーム開始した直後、同一手番中の重要な状態変化、ゲーム終了を取りこぼす可能性がある。
   - サーバー側で永続状態の更新ごとに単調増加する`saveRevision`を更新し、盤面はrevisionの変化を契機に保存する。
   - 複数の保存リクエストが逆順に完了しても、古いレスポンスで`localStorage`を上書きしない。保存済みrevisionより新しい場合だけ反映する。

5. **セーブ形式の互換性ポリシーを定める**
   - `gameVer`不一致の警告だけで読み込まず、互換性判定は`saveVer`で行う。
   - 対応する旧`saveVer`はバージョン別マイグレーションを通し、未知の未来版または移行不能な旧版はルーム生成前に拒否する。
   - 移行・検証失敗時は、利用者に原因と対応可能なバージョン範囲を表示する。

### 推奨対応(P2)

1. **コード衝突時は原則として復元を拒否する**
   - 現行の`players`は切断後も残り、`clients`はSSE接続の集合なので、「有人」「無人」を安定して判定できない。
   - 強制復元を設ける場合だけ、有効な`boardToken`と明示的な確認操作を必須にする。

2. **復元を原子的に行う**
   - 別オブジェクトへ全状態を構築し、スキーマ検証・参照整合性検証・必要なタイマー準備がすべて成功してから`rooms.set()`で一括交換する。
   - 復元時に`clients = new Set()`、`lastActivity = Date.now()`を設定する。失敗時は既存ルームを変更しない。
   - `pick_draw`のタイマー再設定後に処理が二重実行されないことも検証する。

3. **規模と影響範囲を見直す**
   - 復元データは既存ゲームロジックへ直接入力されるため、「既存ロジックへの影響はほぼゼロ」ではなく中程度のリスクを伴う変更として扱う。
   - 実装を、スキーマ/検証、API/認可、UI/自動保存、復元救済、テストの単位に分けてレビューする。

### 追加テスト

1. 認可なし・誤った`boardToken`では保存、復元、終了ができない。
2. 巨大JSON、不正型、範囲外数値、未知カードID、重複プレイヤーID、壊れた参照を拒否し、既存ルームを変更しない。
3. ゲーム開始直後、同一手番中の重要状態、ゲーム終了時にもセーブが作られる。
4. 保存レスポンスを意図的に逆順で完了させても、最新revisionのセーブが残る。
5. 対応旧版はマイグレーション後に完走し、未知の未来版と移行不能版は安全に拒否される。
6. 復元直後の`pick_draw`タイムアウトが一度だけ発火する。
7. 復元失敗時に既存ルーム、SSE接続、保存済みlocalStorageが維持される。

## 7. レビュー回答と最終方針(2026-07-21)

| 指摘 | 回答 | 最終方針 |
|---|---|---|
| P1-1 スキーマ完全定義 | **採用** | 全ルームフィールドを「永続(保存)/表示用履歴(保存)/ランタイム(除外)」の3分類表として仕様化。`makeRoom()`が生成するキー+ゲーム中に追加されるキーを分類表と突き合わせ、**未分類フィールドが現れたら失敗するテスト**を常設(往復一致テストとは別) |
| P1-2 boardToken認可 | **採用** | ルーム作成時に128bit相当のランダム`boardToken`を発行し盤面のlocalStorageへ。`/api/save`・`/api/restore`(・既存の`/api/close`系)で必須。セーブJSONにトークンを含める=ファイル所持者を権限者とみなす。復元JSONは①サイズ上限(2MB) ②形状検証 ③カードIDがカタログに存在 ④プレイヤーID一意 ⑤参照整合性(owners.player・pending対象等)を検証 |
| P1-3 名前復帰のPIN | **オーナー裁定: 即引き継ぎ**(部分不採用) | 指摘は技術的に正しいが、現状`/api/action`自体が無認証(コード所持=任意プレイヤー操作可能)であり、復帰だけPIN化しても全体防御は上がらない。身内プレイ前提で即引き継ぎとする。緩和策: ①**SSE接続中のプレイヤーは名前復帰の対象外**(切断中のみ引き継ぎ可) ②名前は前後空白除去のうえ完全一致 ③参加時に同名重複を拒否。PINはAPI全体に認証を導入する際に合わせて検討 |
| P1-4 saveRevision | **採用** | サーバーは状態変化のたび(broadcast時)に単調増加`saveRev`を更新し、publicStateへ含める。盤面は`saveRev`変化を契機に保存(ロビー開始直後・手番中・終了時もカバー)。localStorageへは**保存済みrevisionより新しい場合のみ**書き込み、逆順レスポンスによる巻き戻りを防ぐ |
| P1-5 saveVer互換 | **採用** | 互換判定は`saveVer`のみで行う(初版=1)。対応旧版はバージョン別マイグレーション、未知の未来版・移行不能版は**ルーム生成前に拒否**し、対応可能なバージョン範囲を表示。`gameVer`は情報表示(不一致は警告のみ) |
| P2-1 衝突は原則拒否 | **採用(1点緩和)** | 有人/無人判定は行わず、同一コードのルームが存在すれば原則拒否。例外: **既存ルームのboardTokenとセーブ内トークンが一致する場合のみ差し替えを許可**(自ルームの二重復元の救済)。強制上書きUIは設けない |
| P2-2 原子的復元 | **採用** | 別オブジェクトに構築→スキーマ/整合性検証→タイマー準備、の全成功後に`rooms`へ一括登録。`clients=new Set()`・`lastActivity=Date.now()`を設定。失敗時は既存ルーム・接続・localStorageを一切変更しない。pick_drawタイマーの単発発火をテストで保証 |
| P2-3 規模見直し | **採用** | 「影響ほぼゼロ」を撤回し中リスクとして扱う。実装・レビューは ①スキーマ/検証 ②API/認可 ③盤面UI/自動保存 ④名前復帰 ⑤テスト の5単位に分割 |
